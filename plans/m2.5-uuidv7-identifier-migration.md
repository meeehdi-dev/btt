# M2.5 — UUIDv7 identifier migration

## Context

M2 is complete and currently uses `crypto.randomUUID()` for domain IDs while Better Auth uses its own text-ID generation. M2.5 must establish a single, time-ordered identifier strategy before M3 adds tickets and further relationships. The MVP baseline is not deployed, so the local database/schema may be reset rather than preserving development-only records.

This is an initial planning draft. No implementation changes are approved or started.

## Approach

- Use UUIDv7 strings at application boundaries and native PostgreSQL `uuid` columns for every generated primary key and corresponding foreign key.
- Use the maintained `uuid` package's typed `v7()` implementation as the shared server-side UUIDv7 generator. This avoids relying on an unavailable `@types/node` declaration for Node's newer native API while remaining compatible with the project's Node 24 server runtime.
- Use that generator for domain creation and Better Auth's supported `advanced.database.generateId` callback. Keep semantic external identifiers/tokens such as GitHub `accountId`, session tokens, verification identifiers, and verification values as text; they are not generated entity IDs.
- Because the app is pre-MVP and undeployed, treat the existing text-ID schema as a disposable development baseline: add a clean schema migration, reset/recreate the local database as needed, and do not design production backfill, rollback, or maintenance-window procedures yet.
- Replace domain `crypto.randomUUID()` creation paths and auth/test configuration together; verify ordering/format, native UUID typing, foreign keys, sessions, and ownership isolation.

## Decisions from user

- UUIDv7 applies everywhere, including Better Auth user, session, account, and verification entity identifiers.
- PostgreSQL should store all generated entity IDs and foreign keys as native `uuid` values.
- The project is not deployed before MVP, so breaking schema changes do not need production backfill, rollback, or maintenance-window procedures at this stage. The local development database may be reset; the repository should retain a clean reproducible schema path.

## Research findings

- Fact: `server/db/schema.ts` currently declares auth and M2 domain IDs/FKs as `text`; domain POST endpoints use `crypto.randomUUID()` (UUIDv4).
- Fact: installed Better Auth 1.7.5 resolves `advanced.database.generateId` before its default generator and passes `{ model, size }`; its built-in `"uuid"` strategy uses `crypto.randomUUID()` (UUIDv4), so it is insufficient for this milestone.
- Fact: Better Auth's official options/database documentation supports a function at `advanced.database.generateId`, and the installed source confirms that this callback is the supported generation boundary for all internally generated models, including user, session, account, and verification records. References: `https://better-auth.com/docs/reference/options`, `https://better-auth.com/docs/concepts/database`, and `node_modules/better-auth/dist/context/create-context.mjs`.
- Fact: Better Auth's schema generator can emit PostgreSQL `uuid` for the built-in `"uuid"` strategy, but a custom UUIDv7 callback does not select that schema path automatically; the project-owned Drizzle schema must explicitly use Drizzle `uuid()` columns.
- Fact: Drizzle exposes native PostgreSQL `uuid()` columns and `defaultRandom()` (which is PostgreSQL `gen_random_uuid`, not UUIDv7); generation therefore belongs at the shared application/Better Auth callback boundary unless a later PostgreSQL UUIDv7 extension decision is approved.
- Fact: the project requires Node 24+, but the installed `@types/node` does not declare `crypto.randomUUIDv7`.
- Decision: use the maintained `uuid` package's typed `v7()` API for the shared generator. This is recommended over Node's newer native `crypto.randomUUIDv7()` because the repository's installed `@types/node` does not declare that API, while `uuid` provides stable TypeScript declarations, server compatibility, and RFC 9562 UUIDv7 support. Reference: `https://github.com/uuidjs/uuid`.
- Fact: current persisted semantic fields such as `account.accountId`, session `token`, verification `identifier`, and verification `value` are not entity IDs and must remain text for provider/token compatibility.

## Resolved planning questions

- Better Auth integration: use the documented `advanced.database.generateId` function in both production and test auth configuration; no adapter fork or database hook is needed.
- Existing local data: reset/recreate the database and keep the MVP schema baseline clean; no development-only record preservation is required.
- UUIDv7 implementation: use the direct `uuid` dependency and its typed `v7()` function. PostgreSQL stores the resulting canonical UUID strings in native `uuid` columns.
