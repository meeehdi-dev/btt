# M45 — Reports and time allocation

> **Plan status: Approved by the human in Plannotator session `pn-edefcf`.** The user approved moving Reports forward as the next product feature in `pn-48030d`; this milestone's detailed scope is now implementation-authorizing.
>
> **Approved review-fix amendment:** [`plans/m45-reports-review-fixes.md`](../../plans/m45-reports-review-fixes.md), session `pn-f60bf4`, refines the completion time-zone contract, selected-filter metadata, grouping focus, and verification. Read it alongside the original scope below.

## Context

The user requested a Reports page in the authenticated shell, with client/project/release filters, weekly/monthly/yearly reporting, Clients/Projects/Releases breakdowns, and a useful visualization of where logged time went. The product discovery and eight user answers are recorded in [`plans/reports-discovery.md`](../../plans/reports-discovery.md), reviewed in Plannotator session `pn-48030d`.

`PLAN.md` currently defers reports to post-MVP. The human has now asked to pull Reports forward as the next planned feature. The agreed primary job is understanding time allocation across clients, projects, and releases. The app stores date-only ticket-linked time entries, ticket estimates, and hierarchy data; it has no billable/rate, revenue, team, or capacity-plan data.

Current reads do not expose period-filtered hierarchy aggregates: `/api/time-entries` requires a ticket, `/api/agenda/week` reads one seven-day interval, and `/api/tickets` exposes all-time per-ticket usage. Reports therefore need a new owner-scoped aggregate read. No database schema change is expected; no chart dependency is currently proposed.

## Out of scope

- Schema/migration, auth/ownership-rule, or deployment changes. No dependency is currently proposed; a chart package may be added only after its exact version and project compatibility are explicitly approved in this plan.
- Billable flags, rates, revenue/invoices, exports, teams/members, capacity/utilization targets, or new time-entry fields.
- Custom/arbitrary date ranges, fiscal calendars, rolling 12-period dashboards, report preferences, or a ticket-grouping tab.
- A separate daily/weekly time-series chart in this milestone; the user explicitly chose no separate trend chart. The selected-period summary/comparison and ranked allocation bars are the agreed first slice.
- A line-by-line detailed report, matched time-entry drawer, or new correction/edit workflows. Row selection filters report aggregates in place.
- Changes to existing Agenda/Ticket Board filters, entity detail pages, time-entry semantics, ticket estimate rules, archive lifecycle, or global search.
- Treating ticket estimates as period budgets or including estimates for tickets that are not Done in the selected period. The estimate metric must state its completed-ticket cohort and lifetime time basis. Because ticket archive/edit operations can also update `ticket.updatedAt`, a later ticket update after Done can move the inferred completion period; this best-effort limitation is accepted under the human's assumption that tickets are not touched after completion.

## Approach

1. **Period model:** add pure date-only helpers in `shared/` for current and immediately previous week/month/year boundaries, using the configured `startOfWeekDay` for weeks. Keep interval ends inclusive at the API/query boundary to match PostgreSQL `date`; test leap years, month/year rollover, week starts, and previous-period equivalence. Keep current selected period and grain as local Reports UI state; no persistence or custom-date URL contract is proposed.
2. **Owner-scoped aggregate read:** add `GET /api/reports` plus a focused server domain query. Validate the period, grouping, and optional hierarchy IDs with the existing Effect handler/schema boundary. Join time entries through ticket → release → project → client and always scope through the signed-in user's client ownership. Aggregate current and prior period totals/group rows in SQL; separately aggregate all-time tracked/estimate data for tickets currently Done whose `updatedAt` is inside the selected period. Return only report aggregates, hierarchy labels/IDs/archive markers, and the distinct hierarchy paths needed to populate cascading filter options. Do not exclude archived entities. Include rows present in either time interval or in the selected-period completion cohort. Avoid using all-time ticket-board aggregates as period totals.
3. **Filters and row selection:** reuse the visual/search/reset conventions from the Agenda and existing `useHierarchyFilters` cascade where it fits. The Reports filter UI contains only client/project/release. Build filter options from hierarchy paths represented in the current period, comparison period, or selected-period estimate-completion cohort, including archived history. Selecting a client/project/release row applies the matching hierarchy filter state and stays on Reports; parent filters are set using the same cascade semantics.
4. **Allocation breakdown:** use Clients/Projects/Releases tabs as the grouping selector; the client/project/release filter bar independently narrows the same report scope. With no hierarchy filter, each tab compares all entities at that level. For example, filter to one client and choose Projects to compare that client's projects. If the selected filter is at or below the active tab's grouping level, a single matching row (or parent row) is expected; switching to a child-level tab exposes its split. Each row's bar/share uses current-period minutes divided by the total for the current filtered scope. Provide exact time, share, and comparison with the same item's prior-period duration. The top summary uses the same current/prior total calculation. Keep sorting deterministic and expose percentages and time as text to assistive technology.
5. **Estimate interpretation:** identify tickets that are currently `Done`, have an estimate, and whose `ticket.updatedAt` lies in the selected period. For each hierarchy group, aggregate that cohort's all-time tracked minutes against the sum of its estimates. A group with qualifying completed estimates but no current/prior interval entries still gets a zero-period-time row with estimate context. Omit the estimate value when the cohort is empty. Keep lifetime estimate usage separate from selected-period logged time/share and explain that `updatedAt` is a proxy under the user's no-post-completion-touch assumption. Do not apply ticket-level ratio colors to the aggregate; keep it neutral and explanatory.
6. **Header and state invalidation:** append Reports and its `g r` shortcut to the existing navigation array. Track the Reports async read with the existing `time-entries`, `tickets`, `hierarchy`, and `settings` resources; `settings` is needed because the configured week start changes report boundaries. Add a new invalidation resource only if source inspection proves the existing map insufficient.
7. **Tests and records:** add tests for date math, current/prior totals and grouped values (including zero/previous-only and archived cases), foreign-user isolation, Done/estimate/`updatedAt` cohort boundaries, tabs/filters/row-selection semantics, keyboard navigation, and same-tab data refresh after approved mutations. Add/index ADR 0061 as Proposed after plan approval; update the product roadmap; record all evidence in this milestone.

### Breakdown control decision — confirmed

In Plannotator sessions `pn-47f4bf` and `pn-168c2d`, the human confirmed the tabs as the grouping selector. The client/project/release filters select the data subset; tabs choose the hierarchy level to compare. Example: with no filter, Clients ranks clients; after selecting one client, Projects ranks that client's projects. When a filter constrains the selected grouping level, a single matching row is expected; selecting a child-level tab exposes its split.

### Estimate cohort proposal and accepted `updatedAt` assumption

For each aggregate row, include tickets with a non-null estimate, current status `Done`, and `ticket.updatedAt` inside the selected date period. Compare the qualifying cohort's all-time tracked minutes (all dates) against the sum of those tickets' estimates; show the comparison only when the cohort is non-empty. A group with qualifying completed-estimate tickets but no time entries in the current or prior report interval still appears with zero period time/share and its estimate comparison. The page's total, share, and period-to-period change remain based strictly on entries dated in their respective report periods and include all ticket statuses.

The human explicitly chose `updatedAt` as the completion-date proxy and no new completion field. This relies on Done tickets not being touched afterward. Fact from `server/api/tickets/[id].patch.ts`: all ticket patches, including archive/restore, update `updatedAt`; therefore an archive/edit after Done can move the inferred completion period. No additional history/schema is planned. Keep this limitation visible in the report's estimate explanation and the ADR.
