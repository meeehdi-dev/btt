# M2.5 — UUIDv7 identifier migration

## Context

M2 domain IDs used UUIDv4 strings while Better Auth generated opaque text IDs. Before M3 adds more product tables and relationships, the project now uses one UUIDv7 strategy across generated auth and domain entity identifiers. The app is pre-MVP and undeployed, so the local database was reset to establish a clean baseline.

## Approved scope

- Use UUIDv7 for generated Better Auth user, session, account, and verification IDs and application/domain IDs.
- Store generated IDs and foreign keys as native PostgreSQL `uuid` columns.
- Use one shared UUIDv7 generator through Better Auth and domain creation paths.
- Update fixtures/tests and verify auth sessions, hierarchy relations, and UUIDv7 format.

## Out of scope

- Production backfill, rollback, dual-column cutover, or maintenance-window procedures before MVP deployment.
- Changing product behavior or archive semantics.
- Adding tickets or time entries.

## Approach

Use the maintained `uuid` package's typed `v7()` function in `server/utils/id.ts`. Configure Better Auth's `advanced.database.generateId` callback in production and test auth configuration, and use the same utility for clients, projects, and releases. Convert all generated-ID and foreign-key columns in the Drizzle schema to native `uuid`; reset the undeployed local database and apply the generated migration.

## Journal

- Fact: installed Better Auth 1.7.5 supports `advanced.database.generateId`; its built-in `"uuid"` mode uses UUIDv4, so the project supplies the shared UUIDv7 callback instead.
