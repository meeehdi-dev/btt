# M3.5 — Ticket board status moves (Complete)

## Context

M3 provides seven fixed ticket statuses and a board with desktop lanes and mobile collapsible sections. The board card currently has only a next-status button: moving from Idea to Done takes six clicks, and a rollback requires opening the edit form. The existing `PATCH /api/tickets/:id` already accepts **any** validated status, including earlier ones and moves out of Done. This is a focused interaction milestone between M3 and M4, not part of the original M3 scope (which explicitly excluded drag/drop).

**Recommendation:** keep this as M3.5 so its drag/drop interaction, accessibility and regression tests get a separate plan and code review. M3 received an explicit human completion declaration and final related-ticket/navigation code review; it is now complete. M3.5 is an independently approved interaction milestone with its own implementation, review and completion gates.

## Approved scope

- On the desktop/tablet board (`md` and up), drag a ticket by a **dedicated handle** to any of the seven status lanes, including an empty lane. Allow skipping intermediate statuses, moving backward, and moving from Done to an earlier status. The handle must not turn the title, hierarchy links, related-ticket shortcuts or next-status button into drag triggers.
- Treat **all seven lanes** as drop targets regardless of the source status: Done → Idea, Idea → Done and every other forward/backward move work the same way. Highlight the lane under the pointer without obscuring its content; dropping back in the current lane is allowed but is a no-op (no PATCH or reorder). Show a moving/busy indication on the source card while saving. Keep the seven-lane horizontal board scrollable; auto-scroll its container near either horizontal edge so a distant lane can be reached without changing the document width. Dropping outside the board does nothing.
- Keep the next-status action but make it a compact **right-arrow icon-only button**, with an explicit accessible name and hover title such as “Move [ticket title] to [next status]”; omit it at Done as today. Provide a compact, labeled **Change status** selector/action on each active card for keyboard and assistive-technology users and as the primary mobile control: mobile uses stacked collapsibles rather than simultaneous lanes, so touch dragging between columns is **not** proposed. The selector permits any different status, including rollback and moves out of Done. Archived cards (when Show archived is enabled) cannot be moved through board controls.
- Use the existing owned, validated `PATCH /api/tickets/:id` with `{ status }`; do not create a new endpoint or relax server ownership/validation. Commit only on a valid drop/selection, await the request and board refresh before displaying the moved card in its destination. On failure leave the ticket in its original lane, display a retryable error and clear busy/drag feedback. Do not mutate relation shortcuts, filters or parent associations.
- No new dependency, schema/migration, auth policy or custom status transitions are proposed. Existing edit-form status changes remain available.

## Human-approved review revision (2026-09-25)

After inspecting the first code-review feedback against the implementation, the human explicitly changed the approved UI scope in chat:

- Replace the dedicated handle with **desktop full-card drag** from noninteractive surfaces, excluding title/hierarchy/related links and buttons. Use a full-ticket drag image that follows the pointer; keep lane highlighting, board-local auto-scroll, and server-backed commits. Give populated lanes generous top and bottom padding as clear drop space.
- Remove the per-card **Change status** selector entirely. Keep the next-status arrow; defer a direct mobile/keyboard control for arbitrary status changes (including rollback and moving out of Done) to a future decision. The existing edit form remains available but is **not** being accepted as an equivalent board interaction. This is an acknowledged accessibility/feature gap, not a claim that mobile drag is supported.
- When an estimate is undefined, render nothing instead of “No estimate” across ticket board, ticket detail, and release detail; remove dangling separators and avoid empty card footers. Preserve the real estimate's clock/duration display.

The original approved plan above/below is kept as historical context; this explicit review revision supersedes its handle/selector and unspecified-estimate requirements. Record the durable mobile policy and compact estimate display in ADR 0010 (superseding the M3.5-specific selector rule of ADR 0009). All API, schema, and dependency constraints remain in force. Revised code must receive another human Plannotator code review before acceptance.

## Out of scope

- Rearranging cards **within** a status lane, persisting sort order, moving tickets between releases, undo/history, real-time sync, changing the set of statuses, or changing the archived-ticket API contract.
- Touch drag between mobile collapsible sections and M6 agenda-block drag/drop implementation. **Human clarification:** drag/drop is desktop-only across the product, including M6; mobile workflows need non-drag controls. This is recorded in ADR 0009 and reflected in `PLAN.md`.

## Approach

1. Reuse `ticketStatuses` as the only status list. Extract a single board-level `moveStatus(ticketId, destination)` action shared by drag/drop, the selector and the existing advance control. Guard against archived, missing, same-status and already-busy tickets before sending a request. Use one in-flight status mutation at a time to avoid conflicting refreshes; treat a same-lane drop as a no-op without a request; rely on the existing API for ownership and enum validation. Do not optimistically change the read model: refresh on success; leave it intact and show an error on failure.
2. Add a small drag handle to `TicketBoardCard.vue` only for active cards at desktop width. Use the browser's native HTML Drag and Drop API (`draggable`, `DragEvent`, `DataTransfer`), with page-level active ticket ID/state and drop handlers on the entire lane (including its empty placeholder). Accept only an active ticket ID found in the currently rendered board and any of the seven `ticketStatuses` lanes (including the source lane as a no-op); reject external/forged drags in the UI (the server remains authoritative). Clear hover/drag state on drop, cancel, filter changes and component teardown. Avoid interference with existing relation hover/pinned highlighting and clicks.
3. Highlight the potential destination lane without changing card border semantics. While dragging near the board's left/right edges, scroll the **board container**, stop scrolling on dragend/drop/cancel, and keep normal page overflow unchanged. If native browser dragging across the overflow boundary proves unreliable during implementation, stop and bring back an alternative for approval rather than silently dropping the edge-scroll requirement.
4. Use the already installed Nuxt UI `USelect` pattern from `app/pages/tickets/[id]/edit.vue` (or an equivalently accessible compact action) for an explicitly named per-card status change. Make the existing next-status action icon-only with `lucide:arrow-right`, a dynamic accessible name and hover title; update any tests relying on its visible text. Verify its component reference before implementation. Ensure focus remains usable if a successful move unmounts/remounts the card; announce success/failure through an accessible status message and keep mouse/keyboard interactions with links and buttons intact.
5. Add focused browser tests with owned fixture tickets: Idea → Done (skip), Done → Idea (full rollback), Done → Review (intermediate rollback), empty-lane drop, cancelled/same-lane drag with **no PATCH**, release-filtered board, off-screen destination auto-scroll, button and related-link clicks unaffected, mobile status selection (390px) and no horizontal document overflow. Verify keyboard status selection and that archive view prevents dragging/changing archived cards. Exercise failure via a mocked PATCH and assert unchanged lane/error/retry; retain existing auth/invalid-status API coverage.
